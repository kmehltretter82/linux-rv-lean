# IRQ monitor project roadmap

## Status update on 2026-11-28: v3 on hold, `irqexit` dropped, follow-up directions

Following Gabriele’s review of RFC v2 and controlled fault-injection experiments on Linux `v7.4-rc1` (lab commit `c76fac0aacccd`), **RFC v3 is on hold** pending Gabriele’s reply:

- **`irqexit` is being dropped.** The `preempt_schedule_irq()` hook sits below the existing `BUG_ON` (which already caught bugs such as powerpc `334f3f6d7a16`), and the monitor cannot observe the early-hardirq interval containing the motivating ARM64 ftrace-recursion counterexample. [LinuxRV/IRQExitAnalysis.lean](LinuxRV/IRQExitAnalysis.lean) now formalizes both sides of this verdict in Lean: under valid stateless guards and `on_cpu` switching, `irqexit` reduces to a 1-bit `(entry, exit)` nesting check (`irqexit_reduces_to_one_bit_nesting`) and cannot decide early-hardirq or return-tail faults (`no_complete_monitor_over_irqexit_alphabet`), while concrete witnesses (`witness_reentrant_entry_direct`, `witness_reentrant_entry_across_switch`, `witness_unmatched_exit`, `witness_on_cpu_fault_while_suspended`) delimit the exact bugs beyond `BUG_ON` that `irqexit` *does* catch.
- **`irqstate` has not yet demonstrated enough incremental diagnostic value.**
  - **E2 (lockdep leaves hardirq context early):** placing the existing macro `lockdep_assert_in_irq()` just before `tick_irq_exit()` in `__irq_exit_rcu()` caught the 2013-style ordering bug 5 ms into boot on both arm64 `PREEMPT` and `PREEMPT_RT`, with zero warnings across 30 s clean workloads (including nested interrupts during inline softirqs).
  - **E3 (injected fault with `irqstate` vs existing lab checks):** no incremental detection was demonstrated for that fault; `lockdep` reported first and then turned itself off, whereas the cross-check counts every mismatch.
- **Design principle from these experiments:** single-point invariants are better served by `BUG_ON` / `lockdep_assert_*()` (in-window, zero tracepoint/RV machinery). A stateful Linux RV monitor only justifies its cost when it checks a genuine multi-event temporal/cross-context protocol or must keep running with `CONFIG_LOCKDEP=n` (e.g., production `PREEMPT_RT` where `CONFIG_PROVE_LOCKING` is off and one-shot lockdep disablement is insufficient).

### Candidate follow-up contributions (so we don't lose track)

1. **Standalone `lockdep_assert_in_irq()` kernel patch** (if Gabriele / `peterz` / `tglx` want it): check other exit/rearm boundaries (e.g., deferred hrtimer rearm), other architectures (x86, arm64, powerpc), and `CONFIG_LOCKDEP=n` builds.
2. **Audit existing *merged* upstream RV monitors (`tools/verification/models/`):** compare upstream JSA-derived monitors (`wip`, `wwnr`, `sco`, `snroc`, `scpd`, `tss`, `snep`, `sncid`, `nrp`)—their `.dot` files, generated headers, and C handler guards—against our Lean JSA 2020 models using the same finite table + guard check that caught the v2 ARM32 guard issue.
3. **Revive `irqstate` only on a concrete `CONFIG_LOCKDEP=n` or multi-event gap:** wait for Gabriele’s answer on whether `irqstate` still has a use case with this coverage before writing v3 patches.
4. **Extend the observability impossibility theorem in Lean:** the `irqexit` case is now proved in [LinuxRV/IRQExitAnalysis.lean](LinuxRV/IRQExitAnalysis.lean) (`every_trace_has_safe_and_faulty_realizations`, `no_complete_monitor_over_irqexit_alphabet`); the next step is lifting the same ETFA-style projection boundary to `irqstate` as a formal pre-implementation design gate for Linux RV monitors.
5. **Advance the timing & scheduling formalization track:** de Oliveira’s thesis ch. 6 latency bounds, Castrovilli & Bini’s *SlackCheck* Theorem 2 (ECRTS 2024), and Prove2Me’s open EDF schedulability Lemma 3.3 (`d7c86d7a-3930-415a-b27f-c17ed287c38d`), alongside self-auditing and submitting Prove2Me JSA 2020 mission proposal `f4dc0e5a-3716-42f0-b9a9-75846e88c4f8`.

## Previous v3 `irqstate` replay plan (paused)

The next deliverable is an executable replay of the standalone `irqstate` monitor on a small set of captured Linux traces. The proposed kernel v3 has four patches covering generic IRQ context tracepoints, `irqstate`, documentation, and focused KUnit tests. On PREEMPT_RT, `irqstate` still needs the existing `sched_switch` event to track the active task's serving-softirq state. [Linux RV v2 RFC and review](https://lore.landau.one/lkml/awNNrVvXCFVPhgk_%40gmail.com/T/)

1. **Pin and validate the monitor contract.** Use the v2 commit below as the current baseline. Once a v3 tree is available, compare every DOT transition and guard with the rvgen header, handler dispatch, and Lean model. Run the [KUnit vectors](IRQ-KUNIT-VECTORS.md) against the model and adapt the applicable cases to the actual v3 handlers. Include nested-depth filtering, RT switch order, and attachment inside an interval. Check state or normal transition events in positive cases so a skipped call cannot pass simply because it caused no reaction.
2. **Replay two real traces.** Use the pinned v2 tree for the first captures if v3 is still in preparation. Take one non-RT kernel trace containing an inline IRQ-exit softirq and one PREEMPT_RT trace containing a serving-softirq task switch. Record the kernel commit and config, CPU, local event order, hardirq depth and guard values at dispatch, softirq provenance, and both task flags for a switch. Record enable/reset boundaries, dropped records, and the kernel verdict. The bare context tracepoints need an explicit capture path. Existing RV transition events provide an output stream for comparison. Make the replay report synchronization skips and the first rejection with its pre-state, event, and failing edge or guard. Use the same replay on a deliberately invalid synthetic trace to check the diagnostic. Count exercised scenarios in live runs as well as reactions.
3. **Prove the replay contract in Lean.** Extend the [SEFM table-monitor result](LinuxRV/Monitor.lean) to sampled guards and the three handler modes. Show that each per-CPU projection has the same monitor states and first rejection under complete, ordered capture, with paired RT events emitted in suspend-then-resume order. Treat a known loss of relevant records as inconclusive until a justified resynchronization point. The [ETFA observation theorem](https://prove2.me/theorems/6ae54bb4-331b-4272-820a-b13e4457105f) supplies the idea of legal completions, which distinguishes possible compatibility from a guarantee about the missing events.
4. **Test startup and ordering separately from the table.** Model the implementation steps for RT attachment, IRQ-off serving-bit update and trace delivery, and non-RT count conversion. Use TLA+ for bounded interleavings and kernel integration runs for emitted-event evidence. Require a source-linked ordering argument for each `softirq.c` change. Pending-work handoff needs its own source and runtime checks.

Use the [completed ETFA mission](https://prove2.me/missions/46d4249d-5a4a-4ae1-b8ef-015475294f12) as the paper baseline. Its CPU/vector partition and IRQ/NMI request alphabet differ from the generic context events used by `irqstate`. The techniques transfer to projection and observation, and any stronger relation between the two alphabets needs a concrete event map and hypotheses. The EWILI scheduling work can proceed independently of this IRQ milestone.

Keep the per-task `irqexit` work as a deferred experiment. Its invocation-order property across switches and migration is distinct. Revisit it when there is a plausible failure that passes the existing scheduler checks and `irqexit` can diagnose, or when a wider return-tail model has a safe, observable completion boundary. In a comparative experiment, derive feasible kernel executions independently of the property being checked and compare both verdicts on the same trace. The existing ARM64 ftrace-recursion result illustrates the current observation gap. A separate research goal is to exhibit two executions with the same monitor inputs and different return-tail outcomes, which would establish the limit for any checker over that alphabet.

## Current results

`LinuxRV/IRQRevision.lean` transcribes both v2 tables and models irqstate event dispatch and RT switch ordering. It models irqexit startup, event processing and reset for one task, plus the proposed v3 owner and startup changes. `IRQExit.run_eq` proves equality of rejection flags and final state for all finite single-task traces when entry, exit and switch-out target the current task and exits have zero hardirq count and interrupts disabled. This is an assumption on inputs, not a proof that the kernel always supplies them; switch-in intentionally does not require current ownership.

The model exhibits a difference on an invalid first exit: v2 processes and rejects it while the proposal starts and skips it. It also exhibits a difference on switch-out from rescheduling when target and current differ. Once the task monitor is already started in idle, an unmatched exit is rejected in both versions. IRQ-state examples cover nested IRQ suppression, a hardirq/softirq nesting path and RT switch ordering.

The model abstracts the hardirq count to zero versus nonzero and uses an ownership bit for the single-task comparison. The finite table check above covers the kernel data and guard expressions. A proof about the running monitor also needs to justify event routing, shared per-CPU state, probe attachment, event production, and concurrent monitor operations. Here `v3` in the `IRQExit` namespace means the earlier proposal to simplify `irqexit` before its deferral.

`LinuxRV/IRQExitAnalysis.lean` builds on `IRQExit` to characterize its exact fault classes (`step_none_iff`, `dispatch_rejected_iff`), prove that under valid stateless local guards and per-task `on_cpu` alternation the 3-state, 4-event monitor (`v2` or `v3`) has the exact same rejection verdict, count, and embedded state as a 1-bit `(entry, exit)` nesting toggle (`irqexit_reduces_to_one_bit_nesting`) and never rejects well-nested traces (`irqexit_never_rejects_under_kernel_invariants`), exhibit separating witnesses that pass every stateless local check yet are rejected by `irqexit` (direct and cross-switch re-entrant `preempt_schedule_irq()`, unmatched `exit`, and `on_cpu` pairing corruption while suspended), and prove that no monitor over the `irqexit` alphabet can decide unobservable early-hardirq or return-tail faults (`every_trace_has_safe_and_faulty_realizations`, `no_complete_monitor_over_irqexit_alphabet`).
